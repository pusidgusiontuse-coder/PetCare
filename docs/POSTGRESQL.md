# PostgreSQL: запуск и перенос SQLite

Основная БД PetCare — PostgreSQL 17+. Python работает через SQLAlchemy и psycopg 3. Схема версионируется Alembic; веб-процессы не создают и не изменяют таблицы. SQLite оставлен для чтения при переносе и быстрых локальных тестов. Автоматического переключения на пустой SQLite больше нет.

## Новый локальный экземпляр

Из корня репозитория, Python 3.12:

```sh
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r app/requirements.txt
cp app/.env.example app/.env
chmod 600 app/.env
```

Задайте в закрытом `app/.env` случайный `SECRET_KEY` не короче 32 символов и `DATABASE_URL=postgresql+psycopg://petcare:ПАРОЛЬ@127.0.0.1:5432/petcare`. Спецсимволы в логине/пароле URL нужно percent-encode. `postgres://` и `postgresql://` также распознаются. Не публикуйте URL с паролем.

Для локального PostgreSQL через Docker Compose:

```sh
read -s POSTGRES_PASSWORD
export POSTGRES_PASSWORD
docker compose up -d --wait db
python -m alembic upgrade head
python -m uvicorn main:app --app-dir app --host 127.0.0.1 --port 8000
```

Введите тот же пароль, что записан в `.env`. Данные PostgreSQL сохраняются в Docker volume. `docker compose down` сохраняет volume; `down -v` удаляет данные. Compose предназначен для разработки, не для настройки production. Не меняйте `SECRET_KEY` при переносе существующего экземпляра: это сохраняет совместимость подписанных токенов и кодов.

## Перенос существующих данных

Для сервера нужна предоставленная хостингом PostgreSQL, сетевой доступ и учётная запись с правами создавать таблицы и последовательности в выделенной базе. Доступность PostgreSQL на тарифе REG.RU этим изменением не подтверждена. Production, тесты и разработка используют разные базы и доступы.

1. Остановите веб-приложение и cron уведомлений, чтобы после копирования SQLite никто не записывал новые данные. Сохраните старую версию исходников и закрытый `.env`.
2. Создайте согласованную резервную копию SQLite через backup API. Источник укажите явно; это **старый** файл, не PostgreSQL:

```sh
python - <<'PY'
import os, sqlite3
from pathlib import Path
source = Path('/PRIVATE/OLD/petcare.db')
backup = Path('/PRIVATE/BACKUPS/before-postgres.db')
fd = os.open(backup, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
os.close(fd)
with sqlite3.connect(source.as_uri() + '?mode=ro', uri=True) as src, sqlite3.connect(backup) as dst:
    src.backup(dst)
PY
```

3. Создайте **новую пустую** PostgreSQL базу. Укажите её в `DATABASE_URL` в закрытом `app/.env`. Не задавайте URL рабочей базы в тестовом окружении.
4. Установите новые зависимости и примените схему. Затем импортируйте копию:

```sh
pip install -r app/requirements.txt
python -m alembic upgrade head
python app/transfer_sqlite.py /PRIVATE/BACKUPS/before-postgres.db
python -m alembic check
```

Команда читает источник в режиме read-only и делает внутренний согласованный снимок. Проверяет целостность SQLite, внешние ключи, набор таблиц/колонок и булевы значения. Все текущие таблицы, включая скрытые PetMatch, пользователей, хеши паролей, сессии, документы и настройки, переносятся в порядке зависимостей. ID сохраняются. Числа, даты и булевы значения преобразуются типами SQLAlchemy; строки не обрезаются. Даты/время остаются совместимыми с текущим приложением: `timestamp without time zone`, для служебных временных меток — UTC.

Транзакция блокирует таблицы назначения, отказывается перезаписывать непустую базу, переносит записи пакетами по 250 строк, сверяет количество строк и SHA-256 всех значений каждой таблицы в порядке первичного ключа. Перенастраивает последовательности ID транзакционно. При ошибке не фиксирует ни одной записи. Отчёт содержит только названия таблиц, количества и контрольные суммы. Исходник не изменяется. Повторный импорт в заполненную базу отклоняется.

Для старой схемы с отсутствующими таблицами/полями сначала обновите **копию** SQLite предыдущей версией PetCare; текущая команда явно откажется от несовпадающей схемы. Не исправляйте осиротевшие ссылки удалением данных без проверки причины.

5. Запустите приложение и проверьте вход старого пользователя, карточки питомцев, документы, совместный доступ, создание/удаление записей и сохранность после перезапуска. Только после проверки включайте cron и принимайте новые записи. Перенос на реальном объёме репетируйте на отдельной закрытой базе.

## Резервные копии и восстановление

`backup.py` теперь делает PostgreSQL backup в custom format. Нужен установленный `pg_dump` той же основной версии, что сервер, или новее. Пароль передаётся через временный приватный service-файл, не через аргументы процесса:

```sh
python backup.py /PRIVATE/BACKUPS/petcare.dump
```

Храните копии вне сервера приложения, с отдельными правами доступа. Проверяйте восстановление в **новой отдельной базе**, передавая подключение через приватный libpq service/`.pgpass`, например:

```sh
PGSERVICE=petcare_restore_test pg_restore --exit-on-error --no-owner --no-acl --dbname=petcare_restore_test /PRIVATE/BACKUPS/petcare.dump
```

Сверьте данные, запустите приложение с восстановленной базой, затем проверьте основные действия. Наличие файла backup само по себе не проверяет восстановление. `alembic downgrade base` удаляет таблицы и предназначен только для пустых тестовых экземпляров; это не способ отката перенесённых данных.

До открытия записи в PostgreSQL откат: остановить новые процессы, вернуть старые исходники и `.env` с SQLite, запустить старую версию на сохранённом исходнике. После начала новых записей нужен отдельный перенос изменений обратно: простое возвращение к старому SQLite потеряет новые данные. Рабочие миграции после выпуска исправляйте новой forward-миграцией.

## Тесты

Создайте отдельную базу `petcare_test` и задайте `TEST_DATABASE_URL`. Тесты создают свежую схему со случайным именем на каждый запуск и удаляют её после завершения. Учётной записи нужны права `CREATE SCHEMA`. Не используйте production URL.

```sh
export TEST_DATABASE_URL='postgresql+psycopg://petcare:LOCAL_PASSWORD@127.0.0.1:5432/petcare_test'
bash scripts/check.sh
```

API-тесты и тесты переноса выполняются на настоящем PostgreSQL. Проверяется перенос всех таблиц и значений, ID после импорта, отказ от непустой базы/неполной схемы/неверных boolean/повреждённых ссылок, полный rollback при ошибке, upgrade/downgrade и отсутствие расхождений схемы с моделями. Без `TEST_DATABASE_URL` pytest использует временный SQLite и **пропускает** PostgreSQL интеграционные тесты — этого недостаточно для проверки миграции.

GitHub Actions поднимает PostgreSQL 17 отдельно для API и браузерных проверок. Браузерные тесты записывают данные; для ручного запуска также создайте отдельную базу, примените миграции и запустите сервер с `ENABLE_DEMO_LOGIN=true`.

Документация: [Alembic](https://alembic.sqlalchemy.org/en/latest/tutorial.html), [PostgreSQL backup](https://www.postgresql.org/docs/current/backup.html), [pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html), [ALTER SEQUENCE](https://www.postgresql.org/docs/current/sql-altersequence.html).
